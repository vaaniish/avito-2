# Локальное усиление до коммерческих интеграций

Этот этап не выполняет production-развёртывание и не подключает S3, домен, TLS,
платёжные договоры или внешние сервисы мониторинга.

## Что изменено

1. Аутентификация переведена на серверные `AuthSession`: случайный токен находится
   только в `HttpOnly` cookie, а PostgreSQL хранит SHA-256-хеш. Это даёт реальный
   отзыв и не раскрывает действующие токены при утечке БД.
2. Frontend больше не хранит пользователя или секрет сессии в `localStorage` и
   всегда подтверждает вход через `/api/auth/me`. CSRF-токен существует только в
   памяти вкладки.
3. Реализованы logout, logout-all, отзыв остальных сессий после смены пароля и
   отзыв всех сессий во всех путях блокировки пользователя.
4. Cookie-mutations требуют `X-CSRF-Token` и доверенный `Origin`; webhook ЮKassa
   исключён только из CSRF и сохраняет собственную проверку.
5. Пул PostgreSQL ограничен и настраивается `PG_POOL_*`, чтобы 1000 VU не могли
   неограниченно создавать соединения.
6. Runtime-preflight запрещает небезопасные production origins, старые JWT env,
   известные demo/default credentials и demo-аккаунты в production-БД.
7. Destructive seed вынесен в `db:seed:demo`, требует явного подтверждения и
   разрешён только для локальной отдельной БД.
8. `perf:1000vu` создаёт изолированные fixtures и 1000 cookie-сессий, выполняет
   ступени до 1000 VU, измеряет event-loop lag и всегда пишет JSON в
   `artifacts/perf/` с последующей очисткой.
9. Тестовые helpers используют cookie + CSRF; JWT unit-тесты заменены тестами
   хеширования, срока жизни и cookie flags.
10. `/health/metrics` скрыт за constant-time Bearer-проверкой или отвечает 404,
    когда токен метрик не настроен.
11. Runtime-логи сериализуются в JSON, получают безопасный request ID и
    рекурсивно редактируют секретные поля. Общий HTTP-log не содержит body,
    query, IP или User-Agent.
12. Shutdown прекращает приём запросов, останавливает worker, ждёт активный HTTP,
    отключает Prisma и принудительно завершает соединения по таймауту.
13. Общий Zod-boundary ограничивает mutation payload, неизвестные поля, глубину,
    массивы и изображения; JPEG/PNG/WebP проверяются по MIME и magic bytes.

## Завершение бесплатного контура

- Все 78 mutation-маршрутов зарегистрированы по `method + route template`; unit
  test обнаруживает новый mutation без схемы.
- Очистка `AuthSession` выполняется через общий promise-lock не чаще заданного
  интервала, а runtime больше не содержит прямых `console.*` вне logger bridge.
- Prisma использует явный `pg.Pool`; защищённые метрики показывают configured,
  total, idle и waiting, не раскрывая строку подключения.
- Добавлены безопасные backup/restore, чистая установка миграций, dry-run audit
  изображений и provider-neutral `ImageStorage`. Inline-режим не может выполнить
  commit миграции во внешнее хранилище.
- Docker/Nginx/systemd/firewall остаются локальными шаблонами. PostgreSQL 16 в
  production-like Compose находится во внутренней сети, backend не root.
- HTTP access log по умолчанию полный (`HTTP_LOG_SAMPLE_RATE=1`); нагрузочный
  harness может отключить успешные строки, сохраняя метрики и все 5xx.

## Локальные команды

```bash
npm run db:migrate:deploy
npm run build
npm run test:unit
npm run test:integration
npm run security:preflight:runtime
```

Demo-seed требует локальный PostgreSQL и явное подтверждение:

```bash
DEMO_SEED_CONFIRM=DELETE_LOCAL_DEMO_DATA npm run db:seed:demo
```

Полный нагрузочный тест требует отдельную БД, имя которой содержит `perf` или
`test`. Backend и harness должны использовать один и тот же URL:

```bash
DATABASE_URL=postgresql://user:password@127.0.0.1:5432/avito-perf \
PERF_TEST_CONFIRM=RUN_LOCAL_1000_VU npm run perf:1000vu
```

Для короткой проверки механики можно временно указать
`PERF_DURATION_SCALE=0.02`; коммерческий отчёт формируется только полным профилем.

Единый локальный gate:

```bash
npm run test:release:local
```

## Последняя локальная проверка производительности

Полный смешанный профиль от 30 июля 2026 года достиг 1000 активных VU и
завершился без падения backend. Итоговый отчёт:
`artifacts/perf/perf_1785448763872_23c743e6.json`.

- 43 682 запроса, 119,47 RPS, event-loop lag p95 2,71 мс;
- пул 20 соединений: максимум 3 845 ожидающих запросов;
- 50 VU прошли целевые p95 без ошибок;
- на 100 VU ошибок ещё не было, но целевой p95 уже превышен для каталога,
  login, создания объявления и checkout;
- первые таймауты mixed-профиля появились на 500 VU;
- итог 1000 VU: 34,55% ошибок и 31,93% таймаутов, поэтому строгий gate честно
  остаётся `FAIL`.

Checkout-fixtures разделены по 100 товарам и 100 продавцам. Отдельный профиль
checkout на 100 VU после исправления выполнил 3 245 запросов без ошибок и
таймаутов с p95 386,57 мс. Значит итоговая деградация mixed-run не объясняется
искусственной конкуренцией за одну тестовую строку. `EXPLAIN ANALYZE` основного
каталожного запроса показал 0,133 мс на текущем объёме; добавлять индекс без
доказанной пользы не стали.

Этот результат фиксирует предел текущей локальной машины и PostgreSQL-контейнера,
а не будущего VPS. Пороговые значения, bcrypt, CSRF, rate limits и таймауты ради
PASS не ослаблялись. После выбора инфраструктуры тот же сценарий нужно повторить.
